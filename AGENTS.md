# Agent instructions

For AI agents (Claude Code, Codex, Copilot and others) working on this repository. `CLAUDE.md` imports this file, so every agent reads the same rules.

## What this project is

Gizmo Sky Radar turns a Seeed Studio XIAO ESP32-S3 (8 MB PSRAM) and a 240 × 240 GC9A01 round display into a live plane radar.

- `microcontroller/` is the PlatformIO firmware. It downloads the aircraft around a location from adsb.fi, draws the radar, and serves the web app, the radar API and a Markdown guide for AI agents (`/llms.txt`).
- `webapp/` is the Nuxt 4 web app, embedded in the firmware: the live Radar page, the Settings page (location, range, units, display), the device card and the Wi-Fi setup. It extends the [gizmo-common](https://github.com/open-gizmo/gizmo-common) web layer, and the mock device in `webapp/server/` answers like the firmware during development, with a simulated sky.

## Structure

- `src/main.cpp`: the entry point; starts logging, the saved settings, the display, Wi-Fi, the web server, the factory reset and the flight data task.
- `src/config`: the project name, the pins of the display (`pins.h`), the shared web server, and the settings of the radar with their limits and JSON (`radar_settings.*`, hardware-free).
- `src/storage`: saves the settings with `Preferences` (gizmo-common saves the Wi-Fi).
- `src/flights`: downloads the aircraft from adsb.fi in a task of its own (`flights.*`), and the hardware-free parts: the readsb JSON parser (`aircraft_parser.*`), the tracker that keeps the trails and moves the aircraft on between downloads (`aircraft_tracker.*`), the download schedule with its backoff (`fetch_schedule.*`), the geography (`geo.*`) and the JSON of an aircraft for the API (`aircraft_json.*`).
- `src/display`: the LovyanGFX driver of the GC9A01 (`panel.h`), the screens (`display.*`), the radar drawing (`radar_view.*`), the colors (`theme.*`) and the units (`units.*`, hardware-free).
- `src/wifi`: gives the radar's names to the gizmo-common Wi-Fi setup, and tells the display how the connection is doing.
- `src/guide`: the Markdown guide for AI agents (`agent_guide.*`), hardware-free.
- `src/server`: the routes of the settings, the aircraft, the guide for agents and the embedded web app (the Wi-Fi setup and device routes come from gizmo-common).
- `src/serial`: the serial log.
- `src/webui`: generated by `npm run build:embedded`, never edited by hand.

The firmware boots, loads the settings, plays the boot animation, connects to Wi-Fi or opens the setup hotspot, and starts the download task. Every 5 seconds the task (on core 0) downloads the aircraft around the location and hands the nearest 64 to the tracker. At about 25 frames a second the main loop (on core 1) draws the radar into a full-screen sprite in PSRAM, from a copy of the tracker taken under a mutex, moving each aircraft on along its track (dead reckoning, in the web app too).

## Working rules

1. Keep the split between firmware and web app clear: no device logic in the web app, no front-end behavior in the firmware.
2. Keep the module boundaries of `microcontroller/src/`: extend the right module instead of adding logic to `main.cpp`.
3. Keep hardware-free logic (`config/radar_settings.*`, `display/units.*`, everything in `flights/` but `flights.cpp`, and everything in `guide/`) free of hardware headers, and test it with `pio test -e native`.
4. ArduinoJson 7 keeps a pointer to a `const char *` instead of copying it: copy any text that isn't a literal (`JsonString(text, JsonString::Copied)`). It also parses short decimals as `float`, so compare coordinates in tests with a tolerance (`TEST_ASSERT_DOUBLE_WITHIN`).
5. When a setting, route, payload or validation rule changes (`/api/config`, `/api/settings`, `/api/reset-settings`, `/api/aircraft`), update the firmware handlers, the mock device in `webapp/server/` and the web app together, and translate every new error ID.
6. The colors of the altitudes and of the themes live in `display/theme.cpp` and `webapp/app/composables/useUtils.js`: change both together.
7. Never call a blocking network request from the main loop: the display must keep its frame rate. Never draw with `fillArc` or `drawWideLine` on the full-screen sprite: they test every pixel of their bounding box and cost a frame.
8. Prefer small, hardware-aware changes: no blocking calls, no needless allocations, no broad refactors unless they are needed.

## With every change

1. **Write the changelog.** When a maker would notice the change (a feature, the web app, the hardware or wiring, the setup steps, a fix), add a line under `## Unreleased` in [CHANGELOG.md](CHANGELOG.md), in the same commit. Write it for the people who flash and use the gadget, not as a commit message: what changed for them, and what they need to do (flash again, rewire, set something up again). Internal changes (refactoring, tests, CI) need no line unless they change what the gadget does.
2. **Keep the docs in sync.** Update the README (and its screenshots in `docs/` when the web app looks different), and tell the user when the gadget's page on [opengizmo.dev](https://opengizmo.dev) needs the same change.
3. **Check it before calling it done.** Run the tests (`pio test -e native` in `microcontroller/`, `npm test` in `webapp/`) and the release build (`npm run build:embedded` in `webapp/`, then `pio run -e release`).

## Releasing

Follow "Releasing a new version" in the README. The version's notes must be moved from `## Unreleased` to a `## vX.Y.Z - YYYY-MM-DD` heading in CHANGELOG.md: they become the GitHub release notes, and the release workflow stops before building anything when they are missing or when notes are left under Unreleased.

Every OpenGizmo gadget has its own release workflow file, and they are kept the same apart from the gadget's name and module (chip), which sit in the `env` block at the top. When you change one, make the same change in the others.

Work on the `feature` branch; changes reach `develop` and then `main` one step at a time, only for a release.
